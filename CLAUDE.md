# CLAUDE.md — как работать над проектом

## 0. Прочитай первым делом

1. **`files/CONTEXT.md` — единственный источник требований.** Прочитай его целиком перед началом
   работы и перечитывай нужные разделы перед каждым этапом. На требования ссылайся по ID
   (R — функциональные, T — технологии, D — сдача, A — допущения).
2. **`files/SPEC.md` — справочник проекта**: §2 стек с обоснованиями, §3 архитектура,
   §4 план этапов, §6 тестирование, §9 правила `files/LEARNING.md`, §10 Definition of Done,
   §11 команды. Читается в начале и в конце этапа (раздел 1.1), не целиком и не каждый раз.
   Нумерация разделов сквозная с этим файлом: здесь §0, §1, §2, §5, §7, §8 — остальные там.
3. Если требование неясно, противоречит другому или его нет — **остановись и спроси Дениса**.
   Принятое решение допиши в `files/CONTEXT.md`, раздел 5, с новым ID `A<N>`.
4. Уровень — **Junior+**: код чистый, понятный, рабочий, без оверинжиниринга.
5. Денис параллельно изучает Django и весь стек по этому проекту. Поэтому `files/LEARNING.md` —
   обязательная часть работы, а не приложение к ней (`files/SPEC.md`, раздел 9).

## 1. Режим работы

### 1.1. Цикл одного этапа
1. Открой `files/SPEC.md`: строку этапа в §4, затронутые части §3, что покрыть тестами — §6.
   Перечитай относящиеся к этапу требования в `files/CONTEXT.md`.
2. Напиши Денису короткий план этапа (3–7 пунктов) и список файлов, которые создашь/изменишь.
3. Создай ветку этапа от актуального `main` (раздел 7).
4. Реализуй код вместе с тестами.
5. Прогони линтер и тесты — всё зелёное.
6. Обнови `files/LEARNING.md` (`files/SPEC.md`, раздел 9) — **до** отчёта, не откладывай.
7. Сделай небольшие осмысленные коммиты (Conventional Commits).
8. Сверься с `files/SPEC.md`, раздел 10.1 (Definition of Done этапа).
9. Отчитайся Денису: что сделано, как проверить руками (конкретные команды/клики),
   открытые вопросы.
10. **Остановись и жди подтверждения.** После «ок» — `git merge --no-ff` в `main` и следующий этап.

### 1.2. Языки
| Где | Язык |
|-----|------|
| Общение с Денисом | Русский |
| Комментарии и docstrings в коде (Python, JS, Vue, Dockerfile, конфиги) | **Украинский** |

## 2. Стек и версии

Обоснование каждого выбора и альтернативы — `files/SPEC.md`, §2. Точные версии фиксируй при
установке: `requirements.txt` — с `==`, фронтенд — `package-lock.json`.
**Перед добавлением любой зависимости, которой нет в этом списке, — спроси Дениса.**

**Backend:** Python 3.14 · Django 5.2 LTS · DRF 3.16+ · PostgreSQL 17 (`postgres:17-alpine`) ·
`psycopg[binary]` 3.x · Redis 7 (`redis:7-alpine`) · Django Channels 4.x · channels-redis 4.x ·
Daphne 4.x · Celery 5.4+ · djangorestframework-simplejwt 5.x · django-simple-captcha 0.6+ ·
Pillow 11+ · redis-py 5.x+. **Dev:** pytest, pytest-django, ruff.

**Frontend:** Node.js 22 LTS · Vue 3.5 (Composition API, `<script setup>`) · Vite ·
JavaScript ES2022 (без TypeScript) · встроенный `fetch` (обёртка `src/api/http.js`) ·
Vitest · ESLint + Prettier из шаблона create-vue.

**Инфраструктура:** Docker, Docker Compose v2, nginx (`nginx:alpine`).

**Не используем:** Vue Router, Pinia, axios, UI-киты и CSS-фреймворки, jQuery/Lightbox2,
TypeScript, django-mptt/treebeard, bleach, django-cors-headers, drf-spectacular/Swagger,
Celery Beat, Flower, Gunicorn/uWSGI. Почему именно так — `files/SPEC.md`, §2.4.

Настройки читаются из переменных окружения через `os.environ` с маленькой функцией-помощником
в `settings.py` — без отдельной библиотеки для env.

## 5. Стандарты кода

### 5.1. Python
- PEP 8; `ruff check` и `ruff format` без ошибок; длина строки — 100.
- Именование: `snake_case` — функции/переменные, `PascalCase` — классы, `UPPER_CASE` — константы.
  Имена говорящие: `build_safe_html`, а не `process`.
- Типизация: аннотации типов у всех функций в `validators.py`, `html_sanitizer.py`,
  `attachments.py`, `captcha.py`, `cache.py`, `broadcast.py`, `tasks.py`. В стандартных методах
  Django/DRF (`get_queryset`, `validate_<field>`, `create`) — там, где улучшает читаемость.
- ООП (R3) там, где оно естественно: модели, сериализаторы, class-based views/ViewSets, consumer,
  класс санитайзера. Не создавай классы ради классов — чистые функции для утилит допустимы.
- Логика не живёт во views: проверка HTML, файлов, CAPTCHA и кэша — в своих модулях;
  views и сериализаторы их вызывают.
- ORM: никаких `raw()`/`extra()`/`cursor.execute` с пользовательскими данными; `select_related`,
  `annotate` — чтобы не было N+1.
- Комментарии и docstrings — **на украинском**. Комментарий объясняет «почему», а не пересказывает код.
  Docstring у каждого модуля и у каждой нетривиальной функции/класса.
- Никаких `print` — только `logging`. Никакого закомментированного кода и `TODO` в `main`.
- Секреты и настройки окружения — только из env; в коде и в `.env.example` — безопасные примеры.

### 5.2. Обработка ошибок
- Ошибки пользовательского ввода — `serializers.ValidationError` (или `django.core.exceptions.ValidationError`
  в валидаторах) с понятным английским сообщением, статус `400`.
- Ловить только конкретные исключения (`PIL.UnidentifiedImageError`, `UnicodeDecodeError`,
  `Comment.DoesNotExist`), никогда `except Exception: pass`.
- Celery-задачи: `autoretry_for` на сетевые ошибки, ограниченное число повторов, логирование.
- Ошибки WebSocket и рассылки не должны ломать создание комментария: комментарий сохраняется,
  ошибка логируется.

### 5.3. Безопасность (R13)
- SQL-инъекции: только ORM и параметризованные запросы; сортировка — через `OrderingFilter`
  с белым списком `ordering_fields`.
- XSS: на фронтенде `v-html` разрешён **только** для поля `text` из API; всё остальное выводится
  через интерполяцию `{{ }}`. URL (`home_page`, `href`) — только `http`/`https`.
- Файлы: проверка по содержимому, UUID-имена, лимит размера и в Django
  (`DATA_UPLOAD_MAX_MEMORY_SIZE`, `FILE_UPLOAD_MAX_MEMORY_SIZE`), и в nginx (`client_max_body_size`);
  защита Pillow от decompression bomb не отключается.
- Production: `DEBUG=False`, `SECRET_KEY` из env, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` (для admin).
- API аутентифицируется только JWT (`JWTAuthentication`), без `SessionAuthentication` — поэтому CSRF
  для API не нужен; admin по-прежнему работает на сессиях с CSRF.
- `X-Real-IP` доверяем только потому, что его выставляет наш nginx; без прокси — `REMOTE_ADDR`.

### 5.4. Санитайзер HTML (ключевой модуль, R19–R20, A8–A10)
- Токенизация регулярным выражением: всё, что начинается с `<` + буква или `/`, — тег;
  остальной текст — обычный текст.
- Проверка по белому списку: тег ∈ {`a`, `code`, `i`, `strong`}; атрибуты только у `a`
  (`href` — обязателен, `title` — необязателен), значения в двойных кавычках; `href` — только http/https.
- Стек открытых тегов: закрывающий тег должен совпадать с вершиной стека; в конце стек пуст;
  `<a>` внутри `<a>` — ошибка.
- При ошибке — `ValidationError` с указанием тега и причины.
- Результат собирается заново: экранированный текст (`html.escape`) + нормализованные теги с
  экранированными значениями атрибутов. Именно он сохраняется в БД.
- Тот же модуль используется при создании комментария и в предпросмотре.
- Клиентская копия правил — `frontend/src/utils/validators.js` (только для UX; решает сервер).

### 5.5. Frontend
- Composition API, `<script setup>`; компоненты — `PascalCase.vue`, composables — `useXxx.js`.
- Один компонент — одна ответственность; сетевые запросы — только в `src/api/`.
- Состояние — `ref`/`reactive`/`computed` и composables, без глобальных сторов.
- Стили — `scoped` в компонентах + CSS-переменные в `styles/main.css`; адаптивность до 360 px.
- Комментарии — на украинском.

## 7. Git

- `main` всегда в рабочем состоянии. Прямые коммиты в `main` — нельзя.
- Ветка на каждый этап (`files/SPEC.md`, раздел 4): `feat/…`, `fix/…`, `build/…`, `docs/…`, `chore/…`, `test/…`.
- Слияние в `main` — только после подтверждения Дениса и только `git merge --no-ff <branch>`
  (A24: ветвление должно быть видно в истории). После слияния ветку можно удалить локально.
- **Conventional Commits:** `<type>(<scope>): <description>` в повелительном наклонении, на английском,
  ≤ 72 символов. Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `chore`, `style`, `perf`.
  Scope: `comments`, `api`, `sanitizer`, `attachments`, `captcha`, `cache`, `ws`, `queue`, `auth`,
  `frontend`, `docker`, `nginx`, `db`.
  Примеры: `feat(sanitizer): validate tag nesting with stack`,
  `test(api): cover ordering whitelist`, `build(docker): add celery worker service`.
- В сообщениях коммитов **нет** трейлеров `Co-Authored-By` и упоминаний инструментов:
  автор коммитов — Денис.
- Коммит — одно логическое изменение, проект после него собирается, тесты к коду — в том же коммите
  или следующем в той же ветке. Никаких `wip`, `fix`, `update` без смысла.
- Не коммитить: `.env`, `files/`, `media/`, `staticfiles/`, `__pycache__/`, `.venv/`,
  `node_modules/`, `dist/`, `.pytest_cache/`, `.ruff_cache/`, IDE-файлы.
- Не переписывать историю `main`, не делать `push --force`. `git push` — только по команде Дениса.

## 8. Чего НЕ делать

- Не выходить за рамки `files/CONTEXT.md` без согласования: никаких рейтингов, закладок, цитат,
  редактирования/удаления комментариев пользователем, GraphQL, Elasticsearch, RabbitMQ, Kubernetes,
  облачных сервисов, TypeScript, SSR.
- Не добавлять зависимости, которых нет в разделе 2, и не оставлять неиспользуемые.
- Не создавать абстракции «на будущее»: базовые классы с одним наследником, репозитории поверх ORM,
  фабрики, generic-сервисы, отдельный слой DTO, лишние настройки.
- Не разбивать `settings.py` на несколько файлов — хватает одного файла и env.
- Не делать несколько вещей в одном этапе и не начинать следующий этап без подтверждения.
- Не «чинить» тесты подгонкой ожиданий под неправильный код.
- Не отключать проверки линтера (`# noqa`) без комментария с причиной.
- Не хранить секреты в репозитории, не логировать пароли и токены.
- Не править `files/CONTEXT.md` молча — только раздел 5 и только после согласования с Денисом.
